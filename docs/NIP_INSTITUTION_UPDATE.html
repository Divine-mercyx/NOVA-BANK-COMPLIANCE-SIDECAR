NIP Institution Codes
Status Update

How we fill in the sending and receiving bank on NIP transfers, what is still missing, and what we need from the bank.

Prepared for: Nova Bank — Compliance, IT & Core Banking (DBA)

Report date: 14 October 2026

Applies to: History extract (TBAADM.HTD) and same-day feed (TBAADM.DTD)

1. Summary

Finacle transaction tables (HTD and DTD) do not say which other bank a transfer went to or came from. The BANK_CODE column is empty on every row we checked.

With the tables shared by the bank team, we found a reliable link. Every NIP transfer now carries the institution code of the other bank, and the bank name where the bank list has it.

In one line: we take the institution code from NIP_OUT_FLW / NIP_IN_FLW, and look up the bank name in NIP_INST_LIST.

2. How it works

Finacle stores each payment as two lines: one debit (money leaving an account) and one credit (money arriving). We pair them into one transaction. For NIP transfers we then add the institution details in four steps.

1

Read the transaction

Pull the debit and credit lines from HTD (past days) or DTD (today). Account names come from GAM.

2

Find the NIP record

Look for the same transaction ID and amount in the NIP out-flow or in-flow table.

3

Take the code

Copy the sending and receiving institution codes from that NIP record.

4

Add the name

Look the code up in NIP_INST_LIST to get the bank name.

Why we match on amount as well: one Finacle transaction ID can hold several payments with different amounts (for example, M00000045 had four). Matching on ID alone would attach the wrong bank.

What the vendor receives

Each transaction in the export now has four institution fields: source code, source name, destination code, and destination name. If we cannot find a real value, the field is left blank. We do not guess.

3. The three limits

These are not bugs. They come from what is stored in the bank's tables today.

Limit 1 — Only NIP transfers are filled By design

Chequebook fees, internal transfers between Nova accounts, RTGS and SWIFT have no row in the NIP tables, so their institution fields stay blank.

Example: the same-day feed on 9 October 2026 had 14 transactions. All were chequebook charges, so all institution fields were correctly blank.

Limit 2 — Outgoing transfers with no sender code Assumption

On outgoing rows, ORIGINATORINSTITUTIONCODE is often empty. Because the money is leaving Nova, we fill the source with Nova's NIBSS code 060003. This is the only value we set ourselves.

Limit 3 — Incoming transfers with no posting ID Data gap

Many incoming rows have an empty POSTING_TRAN_ID. Without it we cannot link the row to the Finacle transaction, so the sending bank stays blank for those payments.

4. What we need from the bank

#RequestWhy it matters
1 Load all banks into NIP_INST_LIST, with their institution codes and names, and keep it updated. Only 7 banks were loaded when we tested. Every code missing from this list shows with a blank bank name.
2 Fill POSTING_TRAN_ID on incoming NIP, or tell us which field links an incoming payment to its Finacle transaction (for example SESSIONID). Removes Limit 3, so the sending bank appears on incoming transfers.
3 Confirm Nova's code for reporting: 060003 (NIP tables), 60003 (vendor sample) or 561 (CBN bank code table). Three different Nova codes appear in different places. The vendor and NFIU need one agreed value.
4 Keep read access for our Oracle user on APIUSER.NIP_OUT_FLW, NIP_IN_FLW and NIP_INST_LIST in production. If access is removed, extracts still run, but all institution fields come back blank.
5 Optional: tell us where RTGS and SWIFT store the other bank, if you want those filled too. Removes Limit 1 for RTGS and SWIFT. Internal transfers and fees will always be blank.

5. Next steps

  1. Bank team completes NIP_INST_LIST (request 1). No code change is needed on our side; names appear on the next extract.
  2. Bank team confirms the incoming link and Nova's reporting code (requests 2 and 3).
  3. We re-run the history extract for the agreed date range so stored transactions pick up the new names.
  4. We share a sample export with the vendor for sign-off.
